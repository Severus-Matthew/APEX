Overview

Speculative decoding speeds up LLM inference by letting a cheap drafter propose tokens that the target model verifies in one parallel pass. But the best drafter and the best draft depth shift from request to request, and from block to block within a request. Any fixed choice either leaves speed on the table or burns compute on tokens that get rejected.

APEX is a learned, two-level controller. APEX-Router picks a speculator (EAGLE-3, n-gram, or a draft model) and an initial depth for each request. APEX-Depth re-selects the draft depth after every verification block, trading speed against wasted tokens.

Integrated into vLLM and evaluated with Qwen3-8B on six workloads, APEX reaches up to 5.24× speedup over autoregressive decoding.

Method

What's new

Choose the drafter, not just the depth

One controller works across different kinds of speculators and picks the right one for each request.

Adapt depth while generating

Draft length is re-chosen after every verification block, using live feedback from the verifier.

Learn where drafts break

Acceptance is modeled as survival: APEX learns how likely a draft is to be rejected at each position, and learns from fully accepted blocks too.

Put a price on waste

A single learned utility balances throughput, accepted progress and rejected tokens when choosing what to do next.

Three operating profiles
APEX-S · Speed APEX-B · Balanced APEX-E · Efficient

The three share one architecture and differ only in the weights of the utility function, which set how much each one favors raw speed over avoiding wasted tokens.

For the survival model, utility, training objectives and full algorithm, read the paper.

Results

Qwen3-8B served in vLLM, six workloads: code (MBPP, HumanEval), conversation (UltraChat-200k), long-chain reasoning (GPQA), long-context completion (The Stack Smol), software engineering (SWE-bench Lite), and math (GSM8K, AIME-style). Baselines are fixed-depth EAGLE-3, n-gram, and draft-model speculation at k ∈ {2, 4, 8, 16}.

What matters

Ablations on a 120-request diagnostic subset (20 per workload). Removing the survival loss hurts waste most; removing verifier-history features hurts speedup most. The same pattern holds for all three profiles; APEX-B shown.

Restricting the candidate depths to k ≥ 3 raises speedup slightly but increases waste and lowers WAS for every profile. The shallow actions are doing real work.

Limitations

  • On code generation, fixed n-gram (k=16) and EAGLE-3 (k=4) beat every APEX profile; routing and utility calibration need work there.
  • Wall-clock results come from one target model (Qwen3-8B) and one serving stack (vLLM), on single-turn prompts.
  • The controller is trained on offline traces and is not updated online. The profiles are not guaranteed Pareto-efficient.
